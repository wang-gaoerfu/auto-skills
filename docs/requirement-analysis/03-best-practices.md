# 需求分析系统 - 最佳实践

## 需求澄清最佳实践

### 1. 提供充分信息

**好的输入**:

```
我想做一个在线教育平台，主要面向大学生。

核心功能：
- 课程视频播放
- 在线作业提交
- 讨论区
- 直播课堂

目标用户：18-25 岁大学生

技术栈：React + Node.js
```

**不足的输入**:

```
我想做个网站
```

### 2. 明确功能边界

明确说明**不做什么**同样重要：

```
功能边界：
- 初期不做课程推荐算法
- 不做移动 App（响应式网页即可）
- 不支持第三方课程导入
```

### 3. 提供量化指标

**好的示例**:

```
性能要求：
- 页面加载 < 2s
- 视频起播 < 1s
- 支持 1000 并发
```

**不足的示例**:

```
性能要求：要快
```

## 文档模板选择

### srs-practical（推荐）

**适用场景**:
- 大多数项目
- 需要正式但不过于繁琐的文档
- 团队内部沟通

**特点**:
- 平衡详细度和简洁性
- 表格化呈现便于查阅
- 包含图表建议

### srs-formal

**适用场景**:
- 大型项目
- 外包项目
- 需要严格遵循标准的场景

**特点**:
- IEEE 830 标准
- 正式严谨
- 适合合同文档

### agile-backlog

**适用场景**:
- 敏捷开发团队
- Scrum 项目
- 快速迭代的项目

**特点**:
- 用户故事为核心
- 包含 Sprint 规划
- 包含故事点估算

### user-story

**适用场景**:
- 小型项目
- 快速原型
- 初期需求探索

**特点**:
- 极简格式
- 快速上手

## 文档组织建议

### 目录结构

```
project/
├── requirements/
│   ├── project-name.md          # 主需求文档
│   ├── changelog.md             # 变更记录
│   └── decisions/               # 技术决策记录
│       └── architecture-decision-001.md
├── design/
│   ├── mockups/                 # 设计稿
│   └── database/                # 数据库设计
└── tests/
    └── acceptance/              # 验收测试
```

### 版本管理

**文件命名建议**:

```
requirements/
├── project-v1.0.md      # 初始版本
├── project-v1.1.md      # 功能增强
└── project-v2.0.md      # 重大更新
```

**或使用日期**:

```
requirements/
├── project-2024-01.md   # 2024年1月版本
└── project-2024-06.md   # 2024年6月版本
```

## 常见问题处理

### Q: 需求变更怎么办？

**最佳实践**:

1. 在文档末尾添加变更记录

```markdown
## 变更历史

| 版本 | 日期 | 变更内容 | 修改人 |
|------|------|----------|--------|
| 1.0.0 | 2024-01-01 | 初始版本 | 张三 |
| 1.1.0 | 2024-01-15 | 新增支付功能 | 李四 |
```

2. 对于重大变更，使用 `/req-clarify` 重新分析

3. 保留历史版本，便于追溯

### Q: 如何处理冲突需求？

**示例**:

```
⚠️ 需求冲突提示

发现以下需求冲突：

1. 性能 vs 功能
   - 冲突：要求高并发，同时要求复杂实时计算
   - 建议：使用异步处理，结果通知

2. 成本 vs 安全
   - 冲突：预算有限，但要求高安全标准
   - 建议：采用托管安全服务，降低自研成本
```

### Q: 需求优先级如何划分？

**P0 - 必须实现**:
- 没有它，系统无法使用
- 例：用户登录、核心业务功能

**P1 - 应该实现**:
- 显著提升用户体验
- 例：搜索、导出功能

**P2 - 可延后**:
- 锦上添花的功能
- 例：主题切换、高级统计

## 与团队协作

### 开发团队

分享需求文档时：

1. **技术章节重点**:
   - 技术栈约束
   - 架构要求
   - 集成接口

2. **验收标准重点**:
   - 可测试的标准
   - 性能指标

### 产品团队

分享需求文档时：

1. **业务章节重点**:
   - 业务背景
   - 目标用户
   - 功能列表

2. **里程碑规划重点**:
   - 交付物
   - 时间节点

### 测试团队

分享需求文档时：

1. **验收标准章节重点**:
   - 所有验收标准
   - 测试方法

## 提示和技巧

### 对话技巧

1. **主动提供信息** - 不要等系统追问
2. **分批描述** - 复杂需求可以分阶段描述
3. **明确术语** - 避免模糊表述

### 文档技巧

1. **使用表格** - 便于阅读和查阅
2. **添加图表** - Mermaid 图表增强理解
3. **保持更新** - 需求变更及时更新文档

### 团队协作

1. **版本控制** - 所有文档纳入 Git 管理
2. **变更记录** - 记录每次变更的原因
3. **定期评审** - 定期回顾需求文档
